# Home Dashboard — Password Hashing Migration (v1.14.0)

## Test mode: DEPLOY-FIRST

## Scope

Fix M3 from audit: local admin password is stored plaintext with a default `"admin"` fallback. Migrate to bcrypt hashed.

## Approach

1. **Schema change:** Add `passwordHash` field on `User` model (nullable). Keep `password` column temporarily for migration compatibility — will be dropped in v1.15.0 after confirming zero live use.
2. **Auth code change:** Update the credentials provider in `src/auth.config.ts` to check `bcrypt.compare(input, user.passwordHash)` if `passwordHash` is set. Fallback to legacy plaintext compare ONLY if `passwordHash` is null AND `password` is set (transition support).
3. **On first successful legacy-plaintext login post-deploy**, silently upgrade: set `passwordHash = bcrypt.hash(input, 12)` and set `password = null`. So no user disruption — the plaintext just quietly gets replaced.
4. **New user creation / password change** — always sets `passwordHash`, never sets `password`.
5. **Migration script:** `scripts/migrate-passwords.mjs` — for any user where `password` is set and `passwordHash` is null, hash it and update. Run once after deploy on both servers.
6. **Remove default `"admin"` fallback:** the code path that seeds default admin with plaintext `"admin"` on first startup — replace with a bcrypt hash of a randomly generated string, printed ONCE to container logs. Ben must copy from logs on first startup. If a user with username `admin` already exists in the DB (which is the case for both servers), this seed path never fires — safe.

## Build & deploy

1. `npm install bcryptjs @types/bcryptjs --save`
2. `npx prisma migrate dev --name add_password_hash` (creates migration SQL)
3. Local build: `npm run build`
4. Manual test on the local dev DB before commit:
   - Create a test user with plaintext password via existing flow
   - Simulate login through the credentials provider directly (write a small test script)
   - Confirm `passwordHash` gets populated and `password` gets cleared
5. Commit and push `main` → MTCD deploy
6. **Immediately after MTCD deploy comes up on v1.14.0:** run the migration script on MTCD:
   ```
   docker exec mtcd_homedashboard-app_1 node /app/scripts/migrate-passwords.mjs
   ```
   Print output. Verify no errors.
7. Push `abraham-prod` → abraham deploy
8. Run migration on abraham:
   ```
   docker exec dashboard-app node /app/scripts/migrate-passwords.mjs
   ```
9. Smoke test on each server:
   - Log in as an existing user with the SAME password they had before. Should succeed.
   - Log in with wrong password. Should fail with 401.

## Rollback

Rollback is trickier because of the schema change. If the deploy breaks:

1. `git revert HEAD --no-edit && git push origin main && git push origin abraham-prod`
2. On each server: `docker exec ... npx prisma migrate resolve --rolled-back <migration_name>` and manually drop the `passwordHash` column via `ALTER TABLE "User" DROP COLUMN "passwordHash";`
3. Users with only `passwordHash` set (created between deploy and rollback) will lose the ability to log in. This is unlikely if rollback is fast.

**Snapshot before deploy:**
- Take a Postgres dump on each server: `docker exec <db-container> pg_dump ... > /tmp/pre-v1.14-backup-<server>-<date>.sql`
- Retain for 14 days.
